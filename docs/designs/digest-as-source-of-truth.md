## Pivot (2026-09-06, /plan-eng-review + Codex outside voice)

**Change:** drop Paketo buildpacks entirely; build `cv_frontend` as a
**distroless Node image from a minimal 2-stage Dockerfile**. This supersedes
every buildpacks/`pack build`/`builder-jammy-base` reference below — where an
older section still says "buildpacks" or "Base stack," read it as "the
Dockerfile build" per this section. T1–T3 are unaffected. T4 shipped green on
buildpacks (runs `33981326429`, `33982413276`); the pivot rewrites T4's build
step and re-opens T4a.

### Why (the wins that survived review)

- **Removes a tool** (`buildpacks` out of `mise.toml`) and a ~1 GB builder
  image pull from every CI run.
- **Both `.trivyignore` CVEs die at the root, not by suppression.**
  CVE-2026-56854 (`golang.org/x/crypto` in Paketo `npm-install`'s `exec.d`
  helper) — that Go binary no longer exists in the image. CVE-2026-59873
  (`node-tar` in Node 24.19.0's *bundled npm*, pulled by Paketo `node-engine`)
  — distroless ships **no npm**, and `cv_frontend` has no `tar` in its own
  `package-lock.json`. Delete both entries only *after* a clean unsuppressed
  scan confirms the components are absent on the shipped platform (Codex #8).
- **Resolves T7's open "buildpacks needs a Docker daemon in-cluster"
  feasibility flag** — a Dockerfile build in Tekton uses kaniko/BuildKit, no
  daemon.
- **Smaller runtime attack surface** — no shell, no package manager, no
  OS userland beyond libc + Node.

### Why NOT (the costs review surfaced — Codex, mostly right)

- Paketo did several things for free that the Dockerfile now owns explicitly:
  prod/dev dep pruning, the `esbuild` native-binary postinstall
  (`allowScripts`), Node-version resolution, non-root user, OCI labels,
  reproducible layer order, `.dockerignore` hygiene. Each is one line, but
  each is now a line *we* maintain.
- Two base-image update streams to track (`node:26` builder,
  `gcr.io/distroless/nodejs26-debian13` runtime) instead of one Paketo
  builder tag. Both **pinned by digest** (this design's own thesis).
- `cv_frontend`'s Remix v3 RC `IMPORT_OUTSIDE_FILE_MAP` runtime crash is
  unchanged by the pivot — buildpacks was never masking it. It makes T4a's
  scope change (below) load-bearing.

## Problem Statement

toolbox is a zero-trust, GitOps module library, but right now nothing in it is
actually pinned by content. Modules are consumed "by source + version pin" —
in practice a git tag or branch ref, which is mutable. `mise.toml` pins every
tool to `latest`. Neither survives contact with the repo's own stated zero-trust
goal. The idea: make the content digest (git commit SHA for git-sourced
modules, sha256 for OCI artifacts) the enforced trust boundary everywhere,
with human-friendly tags as a convenience layer added once signing exists —
never the boundary itself. Paired: bisect-safe commits (one logical,
reversible, testable change per commit) should be an ENFORCED norm in this
repo, not prose in a CLAUDE.md nobody checks.

## Demand Evidence

No incident has happened yet — this repo is day zero (git just initialized
this session, zero commits, all four module directories empty). The stated
evidence is a principle, not a scar: "deterministic behaviors are valued."
That's a legitimate basis for an infra/portfolio project, but it is not
customer demand in the startup sense — named directly rather than dressed up.

The real audience making this concrete: toolbox doubles as a CV/portfolio
project. Named reviewer: a **Platform/SRE/DevOps hiring manager** assessing
supply-chain rigor. Win condition: "this person ships zero-trust for real,
not just as a slogan." Lose condition: "mutable tags = copy-pasted GitOps
tutorial." That reviewer's judgment is the demand signal this design is
built against.

## Status Quo

Today: `source = "git::...?ref=v1.2.0"` (mutable tag) for OpenTofu modules,
`latest` for every mise-managed tool. Landscape research confirms this is a
named, live risk class, not a hypothetical: [zendesk/changed-files
force-retargeted 346 tags to one malicious commit](https://www.reversinglabs.com/glossary/gitops-security-for-the-software-supply-chain),
and [CVE-2026-33634](https://www.penligent.ai/hackinglabs/cve-2026-33634-and-the-trivy-supply-chain-compromise-how-mutable-tags-turned-a-security-scanner-into-a-credential-stealer/)
exists because pipelines treated "pin to a full commit SHA" as optional
advice. Conventional wisdom here is sound, not wrong — this design builds on
it rather than against it: ["tag for discovery, deploy by
digest"](https://safeguard.sh/resources/blog/container-image-digests-vs-tags-why-pinning-matters)
is the accepted GitOps/OCI pattern.

## File Layout (resolved)

Extends this repo's own already-declared pattern (CLAUDE.md's Repo Role:
`modules/*` reusable, a root composition applies them) to Tekton content,
rather than inventing a new one — mirrors [tektoncd/catalog](https://github.com/tektoncd/catalog)'s
kind-first, versioned convention for the reusable pieces:

```
modules/task-buildpacks-build/    # reusable Task: build any app via buildpacks, parameterized by source repo + SHA
modules/task-trivy-scan/          # reusable Task: scan an image, emit CycloneDX SBOM, block on CRITICAL
modules/task-oras-attach/         # reusable Task: attach an arbitrary OCI referrer to a digest
modules/pipeline-build-scan-approve/  # reusable Pipeline: build -> scan+SBOM -> attach SBOM (3 automated Tasks;
                                   # "approve" in the name is the Pipeline's PURPOSE, not a 4th in-Pipeline Task —
                                   # see Approach D for the concrete approval mechanism, resolved below)
deploy/frontend/               # THE instantiation: PipelineRun binding the reusable Pipeline to
                                   # cv_frontend's repo URL + pinned SHA;
                                   #   scripts/approve.sh    - repo owner runs this, outside Tekton (below)
                                   #   scripts/consume.sh    - the consume-side gate: cosign verify-attestation
                                   #   cosign-approval.pub   - committed to the repo (public keys are safe to commit)
                                   #   schema.json           - approval predicate instance; approve.sh populates
                                   #                           its fields (digest, approvedAt, scanReportRef) before
                                   #                           the cosign attest call consumes it
                                   #   tests/*.bats          - consumer bats tests
```

**Concrete approval mechanism (resolved — Tekton has no native
pause-for-human primitive, so this can't be "a 4th Task in the Pipeline"):**
the Pipeline runs `task-buildpacks-build` → `task-trivy-scan` (emits
CycloneDX SBOM) → `task-oras-attach` (attaches the SBOM referrer) fully
automatically, start to finish, no pause. Tekton Chains watches the
Pipeline's TaskRuns independently and auto-attaches its provenance referrer
— also not a Task, a separate controller reacting to TaskRun completion.
**Approval happens after and outside that automatic run, and outside
Tekton entirely**: the repo owner, having read the SBOM and provenance
evidence, runs `deploy/frontend/scripts/approve.sh <digest>` directly —
a plain script, not a Task, not embedded in any YAML. It runs exactly one
command: `cosign attest --predicate schema.json --key
<approval-private-key> <image>@<digest>` — this alone both signs the JSON
schema (Constraints) as the DSSE/in-toto predicate *and* attaches it as an
OCI referrer via zot's Referrers API; no separate `oras attach` or `cosign
sign-blob` step exists for approval (those terms appeared inconsistently in
an earlier pass of this doc — `oras attach` stays scoped only to
`task-oras-attach`'s automated SBOM-attach role, inside the Pipeline). The
approval *private* key (Constraints) never exists inside the Pipeline's
cluster environment; the approval *public* key is `cosign-approval.pub`,
committed to the repo, and is what `scripts/consume.sh` verifies against.
Possession of the private key, not a Task invocation or a registry policy,
is what actually distinguishes this referrer from the automated
SBOM/provenance ones. This isn't a "still
running things locally" gap in the same sense Approach B was — the
repeatable, automated path (build/scan/SBOM) is the real pipeline; a
one-time human judgment call being a script a human runs is the normal
shape of a manual approval gate anywhere (a required-reviewer click in any
CI system is exactly this manual).

`modules/ci-build-frontend/` (created empty earlier this session) is
**removed** — its role is now split across the above, and CLAUDE.md's Tool
Boundaries table row + §Module Structure's named exception for it are
updated to describe this real layout instead of a placeholder name (see The
Assignment). Nothing is lost: the directory was empty.

**OpenBao/Transit placement (added after T3's first ship — this diagram
never covered it originally, a real gap, not a revision of a stated
decision; revised again after a second rework moved it off bare repo
root):** `modules/secret-openbao-local/` is a reusable module — Transit
engine + an arbitrary set of signing keys and access policies + the
rendered `openbao.hcl` server config — instantiated **once**, in
`environments/local/` (`main.tf`). It is not per-consumer: T3's
`approval-key` and T8's future `chains-provenance-key` are two entries in
the same `transit_keys` list, not two OpenBao instances.
`pitchfork.toml` itself stays at the **repo root**, not in
`environments/local/` — pitchfork only discovers the nearest
`pitchfork.toml` searching upward from the current directory, never into
subdirectories, so it has to live somewhere reachable from wherever
`mise` tasks run; its daemon's `dir = "environments/local"` points the
actual `bao server` process at the right working directory without
splitting path conventions. Bootstrap is `mise run openbao-bootstrap`
(`scripts/bootstrap-openbao.sh`), which also stores the root token via
`fnox` (OS keychain) instead of a manual `export`. `deploy/frontend/`
only ever references a key by name (`openbao://approval-key`) — it never
provisions OpenBao itself. Separate from the deferred production
`secret-openbao` module (different lifecycle: local pitchfork-supervised
dev daemon vs. real cluster infra) — see that module's sibling
`secret-openbao-local/README.md` for the full reasoning, and
`environments/local/README.md` for the bootstrap/reset runbook.

**No embedded scripts in Tekton YAML** — this is already this repo's
mandatory global rule ("No code inside configuration files... CI pipeline
steps"), applied here explicitly: every Task step that's a single pinned-CLI
invocation (`pack build`, `oras push`, `oras attach`, `trivy image`) uses
Kubernetes' native `command`/`args` fields directly — no `script:` block, no
inline shell. `deploy/frontend/scripts/approve.sh` (the one place with
real logic — reading evidence, deciding go/no-go) is **not part of any
Tekton Task or Pipeline at all** — it's a plain script the repo owner runs
directly, outside the cluster. That's not a gap in "not very DevOps to run
CLI locally" reasoning: that reasoning was about the *repeatable, automated*
build/scan/SBOM path, which now genuinely is a real pipeline. A one-time
human judgment call is correctly a human running something — that's what a
manual approval gate *is* everywhere (a GitHub Actions required-reviewer
click is exactly as "manual" as this). See Constraints for what makes this
gate a real trust boundary rather than an unenforced formality.

## Constraints

- No home-rolled approval format — confirmed user requirement. Use the
  CNCF/OCI-native mechanism, not a bespoke JSON convention.
- Every tool used already exists as a mise-managed entry (buildpacks, oras,
  trivy, hk, mise, tekton-cli, kubectl) — version-pinning those entries to
  concrete versions (dropping `latest`) is itself part of this wedge's
  deliverables, not a precondition already met.
- **`zot` is also a new pinned tool** (missed in an earlier pass, corrected
  here) — same category as `cosign` below: not in `mise.toml` today. Runs
  as a single static binary on the OrbStack cluster (or locally via `mise`
  for dev), config at `deploy/frontend/zot-config.json`.
- *Public-trust* signing is explicitly deferred — human-friendly tags and
  Fulcio/keyless cosign signing come later. The approval step itself now
  uses a private, unpublished cosign keypair (see the credential-boundary
  entry below) — same decoupling already established for Chains: a
  cryptographic signature exists mechanically, day one, with zero public
  trust claim, exactly as deferred-signing was scoped.
- `hk` remains the sole git-hook gate; no hook logic anywhere else.
- Registry choice must support the OCI 1.1 Referrers API — not a given on
  every registry (older Docker Hub, some self-hosted registries lack it).
  Resolved: `zot` (see Approach D).
- No plaintext registry credential for the automated Pipeline's own
  image/SBOM pushes. **Corrected (outside-voice finding):** Phase 1's GHCR
  push is simpler than earlier described — the standard, documented
  `docker/login-action` pattern for GHCR is `password:
  secrets.GITHUB_TOKEN`, GitHub's own automatic per-job token (short-lived,
  scoped to the workflow run, no static PAT to store or rotate). No
  `id-token: write`/WIF framing needed for GHCR specifically; that
  machinery applies to Phase 2's `zot`, where the network path is verified
  (registry and cluster share a host) but whether OrbStack's k8s API server
  serves `/.well-known/openid-configuration` at
  `kubernetes.default.svc.cluster.local` by default is still an
  implementation-time check, same rigor as the Tiny/Base builder-image
  uncertainty — zot ships a config example for exactly this source
  (`examples/config-bearer-oidc-workload.json`).
- **Approval trust boundary (zero-trust gap, corrected):** the first
  version of this design tried to use zot's registry `accessControl` policy
  to keep the automated Pipeline from self-attaching a fake approval —
  **verified wrong and retracted**: zot's ACL is identity + repository-path
  + action scoped, with no per-artifactType distinction within one
  repository, and OCI referrers must live in the same repo as their
  subject digest to stay discoverable, so there's no registry-policy way to
  grant one identity image/SBOM push while denying it approval push in the
  same repo. Likewise a claimed RBAC restriction on which ServiceAccount a
  Pod/TaskRun may bind to isn't real either — plain Kubernetes RBAC doesn't
  enforce that (Pod Security Admission or Kyverno would, and Kyverno
  enforcement is this design's own deferred Approach C — using it here
  would silently reopen that deferral). **Actual mechanism:** a second,
  distinct cosign keypair — the *approval key* — generated once
  (`cosign generate-key-pair`), its private half kept exclusively by the
  repo owner and never present in the Pipeline's cluster environment.
  `scripts/approve.sh` signs the approval attestation with that key via
  exactly one command, `cosign attest --predicate schema.json --key
  <approval-private-key>` (see File Layout — not a separate `oras
  attach`/`cosign sign-blob` step); the consume-side check runs `cosign
  verify-attestation --key <approval-public-key>` (that public key
  committed to the repo as `cosign-approval.pub`) and only trusts a
  referrer verified against *that specific key* — not merely "a referrer of
  type approval exists." Possession of the private key is the actual
  access control, not a registry policy that (verified) can't express this
  distinction. Reuses `cosign` (already added for Chains) — no new tool,
  and no ServiceAccount/RBAC/accessControl scaffolding needed at all.
  **Corrected (outside-voice finding):** `cosign verify-attestation` by
  default only proves the *signature* is valid — it does **not** enforce
  predicate field values. A `verdict: rejected` record would pass that bare
  check just as validly as `verdict: approved`. Fix, kept declarative per
  this session's own "GitOps declarative first" direction: `cosign
  verify-attestation --policy verdict-approved.cue` — a committed CUE
  policy file asserting `predicate.verdict == "approved"` — not a script
  parsing JSON after the fact. `mise run consume` becomes this one
  `--policy`-bearing invocation, still no separate file/logic needed.
  **Conflict resolution (outside-voice finding, researched):** multiple
  approval-typed referrers can accumulate on one digest (approve, then
  later reject, or vice versa) — resolved by taking the referrer with the
  latest `approvedAt` as authoritative, modeled on GitHub's own PR review
  state machine (a reviewer's most recent submitted review supersedes
  their prior one, not a separate revocation record). Accepted limitation,
  same one Sigstore's own short-lived-cert design exists to avoid at a
  different layer: this can't detect a registry withholding a newer record
  from a query — solving that needs a full transparency log, genuine
  over-engineering at this scale.
  **Human-side registry auth (named, not left implicit):** `approve.sh`
  itself still needs to pull SBOM/provenance evidence from and push the
  approval referrer to `zot` — via the repo owner's own personal
  credential (zot's htpasswd/basic-auth or a personal API token, read from
  `fnox` per this repo's existing steady-state secret pattern), distinct
  from the Pipeline's OIDC-federated workload token. This is a human's
  local auth, not a new mechanism.
- **Acknowledged exception to "no new tool":** Tekton Chains' cosign signing
  backend requires the `cosign` CLI to generate its keypair (`cosign
  generate-key-pair`) — not currently in `mise.toml`. Deliberate, named
  addition: `cosign` joins the pinned stack specifically to back Chains'
  mechanically required signer, not to implement the still-deferred
  public-trust signing story. `orb`/`orbctl` (OrbStack's own CLI) is a
  host-level prerequisite, not a mise-managed entry — same category as
  Docker Desktop, doesn't count against this constraint either way.
- **Approval record has a real JSON Schema** (not an unstructured note —
  this repo's own global standard is "schemas are required for core
  functionality"): `{schemaVersion, digest, verdict, reason, approvedBy,
  approvedAt, scanReportRef}` — `verdict` is `"approved" | "rejected"`
  (eng-review addition: one schema covers both outcomes, modeled on
  GitHub's PR review state machine, always written, never silent — see
  Build Phases), `reason` is free text, `scanReportRef` points at the
  trivy-scan referrer so a decision is traceably tied to the scan it was
  read against. This JSON is the DSSE/in-toto predicate `cosign attest`
  wraps and signs with the approval key above — the signature is the
  envelope around this schema, not an extra field inside it.
- **Signing key custody: OpenBao Transit, not a bare keypair file** (both
  the approval key and, from Phase 3, Chains' provenance key) — see Build
  Phases for the full mechanism and reasoning (native rotation, no key
  material ever leaves OpenBao, zero new tools).
- **Build inputs pinned by digest too (outside-voice finding — a real gap
  in this design's own thesis):** version-pinning `mise.toml`'s CLI tools
  pins what *runs* the build, not the OCI images the build itself consumes
  — the Paketo builder/run images, the Tekton Task container images, the
  GitHub Actions runner image. The whole point of this design is digest
  over tag; applying that only to the outer tools and not the build's own
  inputs is the same gap this design exists to close, just one layer
  removed. Fix: pin ~~`paketobuildpacks/builder-jammy-base`~~ **(pivot: now
  `node:26` + `gcr.io/distroless/nodejs26-debian13`)** and every Task's
  container image by digest (`image@sha256:...`), not a floating tag. This
  constraint is unchanged in intent by the pivot — the *inputs* changed, the
  digest-pin requirement did not.
- **Target architecture: ~~amd64~~ `linux/arm64` (pivot D3 — see the Pivot
  section).** Everything below is the pre-pivot Paketo-era reasoning, kept
  for history: (the original "arm64 only,
  buildpacks defaults to builder-host arch, zero extra config" claim was
  wrong, caught by actually running the pack build dry run named in

## Premises

1. Digest is the enforced trust boundary; human tags are convenience aliases
   only, never the boundary — **revised after cross-model review**: a
   digest alone is content identity, not authority. The actual trust
   boundary is an explicit **approval record** attached to that digest.
2. Git commit SHA already IS the digest-equivalent for git-sourced OpenTofu
   modules (content hash of the tree) — pin `ref=<sha>`, not `ref=v1.2.0`.
   OCI artifacts get a real sha256 digest natively via the registry.
3. Bisect-safe commits are already policy in prose (user's global
   CLAUDE.md) — this repo's job is to enforce it mechanically (an hk gate,
   see Approach D's resolution), not restate it.
4. The build/scan/approve pipeline is the correct wedge: real (unblocks a
   genuinely deferred capability), visible (hiring-manager-legible in ~5
   minutes), has a real external consumer (`cv_frontend` needs
   building/deploying).
5. Retrofitting the three other OpenTofu modules to digest-pinning is a
   separate follow-up phase, out of scope here. **Clarified mid-session:**
   this premise is about the OpenTofu *module* retrofit specifically, not
   "no cluster of any kind." Approach D's dev/CI cluster is OrbStack's
   built-in single-node Kubernetes (`orb start k8s` — one command, no
   OpenTofu, no `cluster-k0sctl` involvement) — a different thing entirely
   from the production cluster this premise defers.

**Rejected during session:** git-committed `approved.json` inside toolbox
itself (a "lateral" alternative floated during Phase 4 drafting) — rejected
before being formally presented, because it's closer to a home-rolled
convention than the OCI-native referrer pattern below, and the user was
explicit about not wanting that.

## Cross-Model Perspective

Codex cold read (independent, structured summary only, no chat access):

- **Steelman:** "A small, executable supply-chain reference that builds the
  actual CV site and permits consumption only of explicitly approved
  artifact digests. Its portfolio value is a five-minute demonstration:
  moving a tag cannot change the deployed bytes, unauthorized replacements
  fail, and every accepted commit passes independently."
- **Most revealing point:** the real external consumer (`cv_frontend`) means
  the first deliverable should be one working source → artifact → consumer
  path with a demonstrated rejection case — and flagged, independently of
  anything asked, that `mise.toml` currently pins every tool to `latest`,
  which contradicts the determinism thesis at the toolchain layer itself.
- **Premise challenged:** #1 — "a digest establishes content identity; you
  also need authority to approve that identity... if [a pull] runs merely
  because the reference contains `@sha256:`, you enforced addressing
  syntax, not trust." This was accepted and folded into premise #1 above.
- **48-hour prototype sketch:** a source-lock file recording the exact
  consumed commit + builder/run-image digests, a build script, a reviewed
  approval record, a consume script that only accepts the exact
  approved digest, bats tests proving tag-retargeting doesn't move
  consumption and an unapproved-but-valid digest is rejected, and CI-level
  enforcement of bisect-safety on every commit in a pushed range.

Follow-up research (this session, general terms only): the CNCF-standard
mechanism for exactly this "approval record on a digest" need is the [OCI
1.1 Referrers API](https://lesitedefrancois.be/en/security/oci-referrers/) —
`oras attach` links an artifact to `<image>@<digest>` as a registry-native
object, no naming convention required. This is the same underlying
mechanism `cosign attest` uses for signed attestations, so the later public
signing upgrade is a drop-in swap on the same referrer slot, not a format
change.

## Success Criteria

- A tag-only reference to the built artifact is provably irrelevant to what
  gets consumed (bats test: retarget the tag, consumption is unaffected).
- A digest with no approval referrer at all is rejected by the consume path
  (bats test).
- A digest carrying an approval-typed referrer that fails `cosign
  verify-attestation --key <approval-public-key>` (wrong/no signature, e.g.
  hand-crafted by an identity that isn't the repo owner) is rejected exactly
  like a missing one (bats test — this is the actual trust boundary, not
  mere referrer presence).
- A CRITICAL-severity trivy finding blocks the pipeline before the SBOM
  attach step is reached (bats test) — proves the scan gate actually
  gates, not just that it runs.
- A build carrying provenance and/or SBOM referrers but no *validly signed*
  approval referrer is still rejected by the consume path (bats test —
  proves the three referrers are not accidentally conflated).
- `mise.toml` carries concrete versions, not `latest`, for every tool this
  wedge touches, including the newly-added `cosign` and `zot`.
- The full path (checkout pinned SHA → build → push → scan+SBOM → Chains
  provenance → attach approval → consume) runs end to end against the real
  `cv_frontend` repo. `orb start k8s` on this Apple Silicon host's native
  `arm64` cluster hosts Tekton Pipelines/Chains (the build engine) only
  — revised this session: consumption/running the approved `amd64` image
  (Constraints: Paketo's builders are amd64-only) happens via a
  `pitchfork`-supervised Docker container on the host directly (T5b), not
  in-cluster. Either way it's under Rosetta emulation somewhere, not
  natively — the cluster's own build execution still needs the same
  emulation question resolved separately (T7's open feasibility flag).
- Every build produces a Chains-generated provenance attestation, verifiable
  with `cosign verify-attestation --key <chains-public-key>` (Chains' own
  keypair, distinct from `<approval-public-key>` used elsewhere) against
  the same digest (proves Chains is actually wired up, not just installed).
- Bisect-safety half of the paired mandate: an hk-declared gate (invoked
  CI-side via `mise run check`, per the resolved mechanism below) rejects a
  non-buildable/non-testable intermediate commit in a pushed range.
- `modules/ci-build-frontend/` no longer exists; CLAUDE.md's Tool
  Boundaries table and §Module Structure describe the real
  `task-*`/`pipeline-*`/`deploy/` layout instead.
- The new `modules/task-*`/`pipeline-*` YAML (Tekton CRDs — genuine k8s
  manifests) passes `kubeconform` (schema validation, no cluster needed)
  before `chainsaw` (live behavior on the actual OrbStack cluster) —
  per CLAUDE.md's own Definition of Done and Testing Strategy. This design
  is the first k8s-manifest-bearing module CLAUDE.md's Testing Strategy
  flagged as "harness prerequisites undefined until built" — resolved here:
  kubeconform needs Tekton's published CRD schemas fetched for offline
  validation; chainsaw needs the OrbStack cluster with Tekton
  Pipelines+Chains already installed, plus readiness checks before
  asserting and cleanup after (teardown the test PipelineRun/TaskRuns).

## Resolved Decisions (no open questions remain)

- **hk bisect-safety mechanism:** a commit-range rebuild-in-isolation check,
  run **CI-side (async)**, not as a blocking local pre-push hook (a full
  isolated rebuild per commit would be too slow for normal dev velocity).
  Still declared in `hk.pkl` — the CI-side variant is invoked via `mise run
  check` (this repo's existing one-definition/two-entry-points pattern),
  not a second, separately-declared check.
- **Approval-record schema:** a real JSON Schema now (see Constraints),
  not deferred to "a second consumer exists" — matches this repo's own
  "schemas required for core functionality" standard.
- **File layout:** resolved — see File Layout section above.
- **zot/trivy tool-boundary overlap:** verified and resolved. zot ships its
  own CVE-scanning extension that also wraps Trivy (separate `trivy-db`
  copy, async 15-minute scheduler). Its known severity-reporting bug (all
  findings "Unknown") was fixed upstream in
  [PR #3943](https://github.com/project-zot/zot/pull/3943) (merged
  2026-04-08, before v2.1.16 — already in our v2.1.20 pin) — not currently
  broken, but still redundant with the `task-trivy-scan` Task and unable to
  serve as a pre-approval blocking gate. Resolution: leave
  `extensions.search.cve` unset in zot's config; `task-trivy-scan` remains
  the one scanner.
- **Registry:** `zot`, verified — supports OCI 1.1 Referrers API
  ([tracked closely, supported](https://toddysm.com/2023/01/05/oci-artifct-manifests-oci-referrers-api-and-their-support-across-registries-part-1/))
  and OIDC Workload Identity Federation ([zot
  docs](https://zotregistry.dev/v2.1.20/articles/authn-authz/)) — single
  static binary, no elevated privileges, self-hostable. A hosted registry
  (GHCR remains the fallback candidate) can still be swapped in later
  without changing the mechanism.
- **Base image / stack:** ~~`builder-jammy-base` only~~ **SUPERSEDED by the
  2026-09-06 pivot (D1/D2):** no buildpacks builder at all. Runtime =
  `gcr.io/distroless/nodejs26-debian13` (pinned by digest), build =
  `node:26` builder stage in a 2-stage Dockerfile. Pre-pivot record: Tiny
  was tried, proven permanently Node-incompatible, dropped. See the Pivot
  section.
- **Target architecture:** ~~amd64~~ **SUPERSEDED by the pivot (D3):**
  `linux/arm64` only. The amd64 constraint was a Paketo-builder limitation
  (their Jammy builders are amd64-only) — distroless is multi-arch, so
  arm64-native is now possible and matches every consumer in this design
  (dev Mac, OrbStack cluster, T5b). Multi-arch deferred to a real amd64
  consumer (TODOS.md).
- **SBOM:** added as a third referrer — see Approach D.
- **Ephemeral debug container:** explicitly deferred to a future session.
- **Approval trust boundary:** a dedicated cosign keypair (not registry ACL,
  not Kubernetes RBAC — both verified insufficient for this, see
  Constraints), held only by the repo owner. Possession of that private key
  is the access control.

  vs buildah, live probe on `orb start k8s`, push to GHCR), T7b (wrap
  `build → scan → oras-attach` as Tasks + `pipeline-build-scan-approve` +

  Each needs its own `/office-hours` + `/plan-eng-review` — not
  implementation-ready. Design lenses named by the owner for that session:
  security, BuildKit-remote, scaling, simplicity, negative space,
  innovation; check fit against the existing pinned stack (Kyverno, Cilium,
  Flux, OpenBao) first. The pre-pivot Phase-2 text below is kept for the
  daemon-feasibility reasoning it captured, but the buildpacks-daemon
  framing is superseded — the question is now "which in-cluster Dockerfile
  builder," resolved by T7a.
  **Real feasibility risk flagged (outside-voice finding), belongs to this
  phase specifically, not Phase 1 (GitHub Actions runners have Docker
  natively):** `pack build` inside a Tekton Task pod does not automatically
  get a Docker-compatible daemon — a k8s Pod isn't OrbStack's host Docker
  endpoint. Resolve at Phase 2 implementation time: either an explicit
  daemon-access decision (rootless build, DinD, and its privilege-boundary
  tradeoffs) or switch to the Buildpacks project's own documented direct
  lifecycle-execution approach for Tekton, which sidesteps needing a daemon
  at all. This is a feasibility spike that belongs *before* the Task YAML
  is written, not discovered during it.
  **Demo consumption — reopened (T5b, was locked via an earlier
  outside-voice finding, now revised):** the original version of this
  paragraph put a `cv-frontend` namespace on this same cluster, with
  `mise run consume` gating a real `kubectl apply`. Revised this
  session: the app's deploy target moves to a standalone
  `pitchfork`-supervised Docker container on the dev Mac instead —
  `orb start k8s` is unaffected, it still exists solely to host Tekton
  Pipelines/Chains (this Phase 2/3 build engine), not the app. Rationale
  (a `/plan-eng-review` + Codex pass, D1-D6): Tekton's k8s dependency is
  about the *build engine*, not a requirement that the deployed app also
  live in-cluster — the same separation this design already applies to
  the approval step itself (which runs "outside Tekton entirely," see
  File Layout). Keeps the cluster architecture-agnostic (arm64-native,
  no amd64-image scheduling concerns) and the app genuinely doesn't need
  orchestration for a single instance.
  Mechanism: `pitchfork.toml` (repo root) gets one `[daemons.frontend]`
  entry whose `run=` always points at a fixed wrapper script
  (`deploy/frontend/run.sh`) — never edited after initial setup, to
  avoid a script mutating pitchfork's own config on every approval. The
  wrapper reads the currently-approved image reference from a
  git-ignored state file (`deploy/frontend/current-image.txt`, written
  **atomically** — temp file + rename — storing the *full*
  `registry/repo@sha256:...` reference so a later GHCR→zot registry
  migration can't silently reinterpret an old file) and **re-verifies
  its cosign approval at launch time too**, not only at consume time —
  via a small shared script (`deploy/frontend/scripts/
  verify-approval.sh`) both `mise run consume` and the wrapper call.
  `mise run consume` writes the new reference, then `pitchfork restart
  frontend`; a real HTTP readiness check on port 44100 (Remix v3's own
  default) after restart reports the truthful result, not an assumed
  success. Concurrent `mise run consume` invocations are a **named,
  accepted constraint** (single-operator CLI tool, don't run it twice at
  once) — not solved with locking, a deliberate scope cut. `docker run`
  stays foreground, no `-d`, no `--restart` — pitchfork is the sole
  supervisor, never two competing ones.
  **What this proves, precisely (Codex catch):** the *pipeline
  mechanism* — right image pulled, container starts under pitchfork,
  readiness genuinely checked — not `cv_frontend`'s own correctness.
  `cv_frontend` currently crashes at runtime with a Remix v3
  `IMPORT_OUTSIDE_FILE_MAP` error (T4a's dry run, a different repo's
  bug) — T5b's acceptance criteria account for this explicitly rather
  than blocking on unscheduled work elsewhere. Still explicitly a
  **demo/proof** mechanism, not where the real public `cv_frontend` site
  lives — actual public hosting (Vercel/Netlify, or the eventual
  `cluster-k0sctl` production cluster) stays a separate, tracked decision
  (TODOS.md), unaffected by this change.

- **Phase 3** (Tekton Chains): install Chains on Phase 2's cluster. Its
  provenance-signing key is **also OpenBao Transit-backed** (eng-review
  DRY finding — Chains' signer config supports arbitrary KMS backends
  including the `hashivault://` family OpenBao answers to; a second Transit
  key, e.g. `chains-provenance-key`, in the same already-running OpenBao
  instance replaces a second, separate k8s-Secret-stored raw keypair — one
  secret-management approach for every signing key in this design, not two).
  Purely additive otherwise — does not touch the approval mechanism.
  **OpenBao access policy, made explicit (outside-voice finding):** once
  signing is a remote call (`transit/sign`), permission to invoke it *is*
  the signing power — "the private key never enters the cluster" proves
  the material can't be exfiltrated, but doesn't by itself stop the
  Pipeline's own identity from calling sign on the *approval* key if its
  OpenBao policy allows it. Fix: Chains' OpenBao auth path gets a policy
  scoped **only** to `chains-provenance-key`, explicitly denied
  `transit/sign` on `approval-key` — the human's local auth (Constraints)
  is the only identity with that grant. **Rotation's trust-distribution
  gap (outside-voice finding):** OpenBao Transit's key versioning keeps old
  versions so pre-rotation signatures still verify, but the *exported
  public key* changes on rotation — `cosign-approval.pub` (committed to
  the repo) must be re-exported and re-committed after any rotation, or
  `mise run consume` verifies against a stale key for new signatures. Add
  this as an explicit step in the rotation procedure, not left implicit.
  **Provenance binding (outside-voice finding, Phase 3 implementation
  detail):** Chains signs *asynchronously* after a TaskRun completes, and
  needs the Task to declare its image result explicitly (Tekton's
  documented `results`/`type: image` mechanism) to bind provenance to the
  *correct* digest — installing Chains alone doesn't establish this
  source-to-image relationship. `mise run consume`'s check for a
  provenance referrer needs a bounded wait (Chains' signing isn't
  instantaneous), not an assumption it's already there the moment the
  Pipeline finishes.

- **Phase 4** (hk bisect-safety CI gate): a real script
  (`check-history.sh`, rebuild-in-isolation per commit — no existing tool
  does this), invoked via `mise run check` (this repo's existing dual
  entry-point pattern). Independent of Phases 1-3, can land in parallel
  with any of them. **Scope clarified (outside-voice finding):** the gate
  proves **historical buildability** only — "this commit's build/test
  suite passed, using the tool versions pinned AT that commit" — a stable,
  re-runnable fact. It does not re-check today's security/CVE policy
  against old commits (an untouched commit from months ago shouldn't start
  failing because a new CVE was discovered — that's what present-tense
  trivy scanning on current builds is for, a separate concern). `git
  bisect`'s own purpose is finding regressions by walking history
  reliably, not re-litigating security posture. **Wired as a GitHub
  required status check** — without branch-protection configuration, a
  CI-side check is informational, not blocking.

Each phase is this review's actual unit of Architecture/Code
Quality/Tests/Performance scrutiny, not the ~20-file whole.

**Stopping-rule acknowledgment (outside-voice finding):** Codex's sharpest
meta-critique was that this design has no stopping rule — Tekton, Chains,
`zot`, and a locally-operated KMS are each individually justified partly by
"it's already pinned in mise," which isn't the same as a concrete unmet
requirement. That's a fair challenge to this session's own trajectory, not
just a Phase-N detail. The honest answer: Phase 1 alone (GHCR + GitHub
Actions + OpenBao-backed signing) already delivers everything Premises #4
actually requires — a real external consumer, a real digest, a real
enforced approval gate, reviewer-legible in 5 minutes. Phases 2-3 are
justified specifically by `tekton-cli` already being a *stated intent* in
this repo's own CLAUDE.md (not just "happens to be pinned"), not by
default. If that stated intent didn't exist, the honest recommendation
would be: ship Phase 1, stop, and let a second real requirement — not
portfolio optics — justify Phase 2's complexity before building it. Additional test
coverage locked this review, beyond what Success Criteria already listed:
a bats test proving the buildpack build actually succeeds against a
real checkout (not just a manual dry run — moot for the Tiny→Base
fallback specifically, since Tiny was later dropped entirely rather than
kept as a permanently-failing branch to test), a bats test exercising
the explicit-rejection branch
(verdict=rejected still produces a signed, consume-rejected record), and
an integration test proving OpenBao Transit key rotation doesn't break
verification of pre-rotation referrers. GitHub's automatic per-job
`GITHUB_TOKEN` is scoped to the workflow run and requested implicitly by
`docker/login-action` at push time, not a long-lived credential fetched
once at job start — mid-build expiry doesn't apply the way it would for a
separate OIDC federation flow — documented, no test needed.

**OpenBao storage backup (eng-review critical gap):** the Transit storage
directory itself — not just the key it holds — has no backup story;
losing it destroys both signing keys at once, the same
single-point-of-failure this design fixed at the keypair level, moved one
layer down. Resolution: periodic `bao operator raft snapshot save` (not a
raw directory copy — revised after T3 switched OpenBao from the
deprecated `file` backend to `raft`; a plain file copy of a live raft
store can grab its bolt-based FSM mid-write) with a documented restore
procedure — not a new tool, `bao` already ships the snapshot command.

  distroless runtime) is the industry-standard Node containerization

  invented.
- `hk`'s existing "one definition (`hk.pkl`), two entry points (`mise run
  check`)" pattern is reused for the bisect-safety CI gate, not duplicated.

## Worktree parallelization strategy

| Step | Modules touched | Depends on |
|---|---|---|
| Phase 0 (mise.toml + CLAUDE.md) | root files only | — |
| Phase 1 build/scan (GHA workflow) | `.github/workflows/`, `deploy/frontend/` | Phase 0 |
| Phase 1 approve/consume (OpenBao + cosign) | `deploy/frontend/scripts/`, `environments/local/`, `modules/secret-openbao-local/` | Phase 0 |
| Phase 4 (hk bisect-safety) | `hk.pkl`, CI config | — (independent of everything) |
| T5 approve/consume | `deploy/frontend/scripts/`, `mise.toml` | Phase 1 proven |
| T5b demo deploy | `pitchfork.toml`, `deploy/frontend/` | T5 |
| Phase 2 = T7a→T7b→T7c (Tekton) — **own planning session each** | `modules/task-*`, `modules/pipeline-*`, cluster | **T5 + T5b done** |
| Phase 3 (Chains) | Tekton install, OpenBao (2nd Transit key) | Phase 2 |

**Lanes:**
- Lane A: Phase 0 → Phase 1 (sequential, both touch `deploy/frontend/`
  and root config).
- Lane B: Phase 4 (independent — `hk.pkl` only, no shared modules with
  Lane A).
- Launch A + B in parallel worktrees. Phase 2 and Phase 3 wait for Lane A
  to land (they build directly on Phase 1's proven mechanism) — sequential
  after A, not parallelizable with it.

**Conflict flag:** none — Lane A and Lane B touch disjoint directories.
